#### 尝试"limit_req to stop certain URLs from being abused" 

 目前压力测试有几个类似bug都是由于短时间服务器收到大量请求导致服务器负载高，导致后续执行出错。对于这类问题我和树峰讨论下准备引入 nginx 的 高并发限流模块功能。我们之前应该都没用过这个功能，所以需要和大家说明下。 nginx 的 高并发限流模块功能 常见 双十一抢购时候，有时候提示"服务器现在负载过高请稍后再试"。

但首先有一点明确，当高并发请求发生时候肯定是采取多种手段一起（甚至包括升级硬件），单一手段是没法完全解决问题。   我们引入这个模块能效果是当短时间收到大量并发请求时候，利用nginx这个功能把过多请求直接返回 503，这样保证服务器不会过载，已经在处理的请求不受影响。 比如对于 "12288 持续调用PC客户端获取token接口，CM服务器负载过高" 和 "12235 预置130个预览式外呼任务，总客户量17w左右，企业以2Tps速率获取客户，管理平台（CM）FPM模块load到20以上，CPU占用到100%" 都是因为 token这个接口短时间收到过多请求。我们现在要设置对这个接口允许的同时并发连接数，每秒20个（只是一个例子）。这就意味着每秒最多20请求，再多就503. 这个数字设置多少合适需要大家意见，实际效果如何要在看。

#### nodelay



发现设置`nodelay` 一个有趣结果： https://www.nginx.com/blog/rate-limiting-nginx/

> Now suppose that 101 milliseconds after the first set of requests was forwarded another 20 requests arrive simultaneously. Only 1 slot in the queue has been freed, so NGINX forwards 1 request and rejects the other 19 with status `503`. If instead 501 milliseconds have passed before the 20 new requests arrive, 5 slots are free so NGINX forwards 5 requests immediately and rejects 15.

当前 slot有几个是空闲，就接收几个请求，所以当sleep 0.5 秒往往有4个拒绝，sleep 1秒就都能处理

如果不设置nodelay, The `burst` parameter defines how many requests a client can make in excess of the rate specified by the zone. 所以sleep设置成0.1秒都没问题，正常处理。

### 6.15

#### socket.io

[Why you don’t need Socket.IO](https://codeburst.io/why-you-don-t-need-socket-io-6848f1c871cd)

[Vanilla websockets vs socket.io](https://gist.github.com/zeusdeux/5491cff541fb4ac4c142) 

> - Native websockets provide us with only a `send` method to send data to the server...  Socket.io lets us emit arbitrary events with arbitrary data (even binary blobs) to the server.
> - To receive messages on a vanilla websocket you can only assign a handler for the `message` event. The data you receive is mostly likely to be text (again not too sure about this) and you will have to parse it manually before consuming it. Socket.io lets the server and client both emit arbitrary events and handles all the parsing and packing/unpacking.
> - Socket.io gives us both a server and a client. Implementing a vanilla websocket server isn't something that you would want to do per project since it's quite painful. You will have to implement [RFC6455](https://tools.ietf.org/html/rfc6455) to have a compliant websocket server. [Here's](https://developer.mozilla.org/en-US/docs/WebSockets/Writing_WebSocket_servers) a gist of what writing one involves. [Here's](https://github.com/websockets/ws/blob/master/lib/Receiver.js#L183) what parsing an incoming packet on the server looks like (all packets from clients should be masked as per the specification).
> - Socket.io gives us abstractions like rooms which aren't really part of the websocket spec so you will have to roll your own if you want to use vanilla websockets.

[Differences between socket.io and websockets](https://stackoverflow.com/questions/10112178/differences-between-socket-io-and-websockets)

> 1. socket.io allowed me to send/emit messages by specifying an event name.
> 2. In the case of socket.io a message from server will reach on all clients, but for the same in websockets I was forced to keep an array of all connections and loop through it to send messages to all clients.
> 3. clustering with Socket.io is not a big deal. Socket.io offers [Adapters](https://socket.io/docs/using-multiple-nodes/#passing-events-between-nodes) that can be used to link it with Redis to enhance scalability.

#### cancel await

[Are there any JS constructs where it's unsafe or ill-advised to use async/await?](https://www.quora.com/Are-there-any-JS-constructs-where-its-unsafe-or-ill-advised-to-use-async-await) [Answered April 14, 2020](https://www.quora.com/Are-there-any-JS-constructs-where-its-unsafe-or-ill-advised-to-use-async-await/answer/Corey-Butler)

**Don’t use async/await when you think you may need to cancel an operation**. For example, consider a data processing pipeline. If a data operation times out, you may not actually be able to stop the process. It comes down to a language problem with promises, since there’s no real way to externally cancel a promise (which is the basis of async/await).Syntactically, I like async/await and use it in limited circumstances. Conceptually, this particular failure of JS has bitten me several times. Personally, I’m a big fan of event-driven systems, which are entirely async. The real challenge is sequencing a flow of events, i.e. waiting for the results of one process in order to use them in another. Sequencing is necessary from time to time, but it contradicts some of the practices humans prefer to use in event-oriented architecture.I tend to favor an event bus approach. I wrote a lib called [coreybutler/shortbus](https://github.com/coreybutler/shortbus) years ago and it has been a stable part of how I handle sequential and parallel processing without async/await. It’s quite straightforward, basically a mini event bus controller that looks like a task runner. If you’ve ever used Express middleware, you’ll feel right at home. Kyle Simpson also made a similar library called [getify/CAF](https://github.com/getify/CAF). It’s a similar concept, but leverages generators with token cancellation, and a different syntax.The issue is being addressed by TC39, but progress is very slow.

```javascript
inp.pipe(gzip).pipe(out);
//using pipeline
pipeline(
  fs.createReadStream('The.Matrix.1080p.mkv'),
  zlib.createGzip(),
  fs.createWriteStream('The.Matrix.1080p.mkv.gz'),
  (err) => {
    if (err) {
      console.error('Pipeline failed', err);
    } else {
      console.log('Pipeline succeeded');
    }
  }

```

In this example, we use `.pipe()` to get the data source from one end to the other. However, notice there are no proper error handlers attached. If a chunk of data were to fail to be properly received, the `Readable` source or `gzip` stream will not be destroyed.

for Node.js 10.x or later version, [`pipeline`](https://nodejs.org/api/stream.html#stream_stream_pipeline_streams_callback) is introduced. This is a module method to pipe between streams forwarding errors and properly cleaning up and provide a callback when the pipeline is complete.
